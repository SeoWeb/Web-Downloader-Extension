## Context

In server mode the extension downloads every `<img>` resource, computes a local filename, uploads the blob to the Python backend, and uploads a `filename_map` (original URL → local path) that the server uses to rewrite HTML during ZIP assembly.

The filename for extensionless URLs (URL paths whose last segment contains no dot) is generated by `generateImageFilename(urlSrc, contentType?)` in `src/background/urlUtils.ts`. When `contentType` is absent, the function hard-codes `extension = "bin"`. The calling site in `src/background/fileHandlers/images.ts` reads the content-type from `result.response.headers.get('Content-Type')`.

`RequestQueue` (`src/utils/RequestQueue.ts:482-547`) fetches third-party resources and, when CORS fails, silently retries with `mode: 'no-cors'`. The resulting `Response` is **opaque**: per the Fetch spec, `response.headers` is an empty list and `response.body` yields an unreadable stream — except that calling `.blob()` still produces a blob containing the real bytes (with `blob.type === ''`). This is the dominant failure mode for third-party CDNs such as `store.storeimages.cdn-apple.com`, whose URL `.../icon-product-mac?wid=225&fmt=png-alpha` has no path-segment extension.

There is already a server-side `content-type-aware-fallback` capability that, when `filename_map` misses, consults a `content_type_map` built from `Resource.content_type`. But this fallback is never exercised for the failure mode above because:
1. The client bakes `.bin` into `filename_map` before upload, so the filename-map *hits* with the wrong path.
2. `fileHandlers/images.ts:98` calls `storage.addFile(path, blob)` without a content-type argument, so `ServerStorageAdapter.addFile` defaults `contentType = "application/octet-stream"` and the server stores that garbage MIME.

The fix must therefore happen **on the client**, before filename generation, and must not rely on readable response headers.

## Goals / Non-Goals

**Goals:**
- Recover the correct image MIME type from the blob bytes alone, so that `generateImageFilename` produces a real extension (`.png`, `.jpg`, `.webp`, …) instead of `.bin` for opaque / extensionless fetches.
- Plumb the recovered MIME through the existing `storage.addFile(path, blob, contentType)` signature so that `Resource.content_type` server-side is correct for any future fallback that relies on it.
- Zero behavioral change for images that already succeed today (URL has extension, or response has readable `Content-Type`).
- Keep the fix strictly client-side — no server, protocol, or schema changes.

**Non-Goals:**
- Detecting arbitrary binary formats (PDFs, fonts, video) — only the image types the filename table understands.
- 100% accuracy against adversarial inputs. A sniffer that returns `null` on unknown content and lets the caller fall back to `.bin` is acceptable; it merely must not return a wrong MIME for a clearly-recognizable signature.
- Re-architecting `RequestQueue` to avoid opaque responses. (That was evaluated as option C in plan mode and deferred.)
- Back-propagating the real remote URL into `ServerStorageAdapter.originalUrl`. Out of scope; tracked separately.

## Decisions

### Decision: magic-byte sniffing runs client-side, post-fetch, pre-filename

**Choice:** Add an async `sniffImageMimeType(blob: Blob): Promise<string | null>` that reads the first 512 bytes and matches binary signatures, then invoke it from `fileHandlers/images.ts` between obtaining the blob and calling `generateImageFilename`.

**Alternatives considered:**
- *Server-side sniffing on resource upload.* Rejected: the extension has already committed a `.bin` filename into `filename_map` by the time the server sees the bytes, so we would have to negotiate a rename. Cross-cutting and fragile.
- *Fetch with `mode: 'navigate'` instead of `no-cors`.* Partial fix — navigate mode does return readable headers in Chrome — but doesn't work for every origin and still benefits from sniffing as a safety net. Adds protocol complexity. Deferred.
- *Parse hints from the URL query string (e.g. `fmt=png-alpha`).* Fragile, CDN-specific, doesn't generalize. Rejected.
- *Use a third-party library (e.g. `file-type`).* Pulls ~30KB into the extension bundle for a problem solvable with ~80 lines of native code. Rejected.

### Decision: which signatures to recognize

**Choice:** PNG, JPEG, GIF (87a/89a), WebP, BMP, ICO, AVIF, HEIC, TIFF, and an SVG text sniff. This set matches 1:1 the image-extension list in `generateImageFilename` (`urlUtils.ts:454-456`) and the MIME→ext table (`urlUtils.ts:368-384`).

**Rationale:** Sniffing any MIME the caller wouldn't know how to turn into an extension is waste; sniffing any image format on the accepted list is useful.

### Decision: SVG via bounded UTF-8 text sniff

**Choice:** If no binary signature matches, decode the first 512 bytes with `TextDecoder('utf-8', { fatal: false })` and return `image/svg+xml` if `/<\?xml\b|<svg\b/i` matches.

**Alternatives considered:**
- Strict regex requiring `<svg` before any other tag. Rejected — real-world SVGs are often preceded by `<?xml` declarations, comments, or a stray BOM/whitespace.
- Skip SVG sniffing entirely. Rejected at user's direction (see proposal user preference).

**Trade-off:** A non-SVG XML document would also match `<?xml`. For images this is nearly impossible in practice; and the downside is a `.svg` extension rather than `.bin`, which is not worse.

### Decision: invocation condition in `fileHandlers/images.ts`

**Choice:** Invoke the sniffer when `contentType` is empty or `'application/octet-stream'`. Treat those two equivalently: both are the "don't know" cases.

**Alternatives considered:**
- Always sniff, ignore header. Rejected — wastes work on the common happy path and could override a correct `image/svg+xml` with a mis-sniff if the SVG happens to look binary.
- Sniff only on empty string. Rejected — octet-stream from misconfigured CDNs is just as much a "don't know" signal.

### Decision: single new module, not inlined in `urlUtils.ts`

**Choice:** Create `src/background/sniffImageMime.ts` (per user preference). Keeps the sniffer's binary-byte logic testable in isolation and avoids bloating the already-large `urlUtils.ts`.

### Decision: pass `contentType` to `storage.addFile`

**Choice:** Update the call at `fileHandlers/images.ts:98` from
```ts
await storage.addFile(`images/${filename}`, blob);
```
to
```ts
await storage.addFile(`images/${filename}`, blob, contentType || undefined);
```

**Rationale:** `ServerStorageAdapter.addFile` already accepts `mimeType?: string` and defaults to `application/octet-stream`. No interface change is needed; we just need the caller to stop passing `undefined`.

**Alternative considered:** Make `ServerStorageAdapter` fall back to `blob.type` internally. Rejected because opaque-response blobs have empty `blob.type`; the caller has strictly more information than the adapter, so the caller should pass it.

## Risks / Trade-offs

- **Risk: false negatives (sniffer returns null for a real image).** Mitigation: the pre-existing `.bin` fallback is preserved; no download fails. Net effect is status quo for that image.
- **Risk: false positives (sniffer misidentifies bytes).** Mitigation: all recognized signatures are 2–12 bytes of fixed magic; collision probability with arbitrary data is negligible. SVG text sniff is the weakest link but bounded to 512 bytes and regex-gated.
- **Risk: reading 512 bytes of every image adds latency.** Mitigation: sniffer only runs when `Content-Type` is missing or `octet-stream` — rare on the happy path. Reading 512 bytes from an in-memory Blob is a microsecond-scale operation.
- **Risk: HEIC/AVIF recognition is imprecise because `ftyp` boxes cover many brands.** Mitigation: we include the common image brands (`heic/heix/hevc/hevx/heim/heis/hevm/hevs/mif1/msf1` for HEIC, `avif/avis` for AVIF). Rare brands return `null` and fall back to `.bin` — same as today.
- **Trade-off: test fixtures need to be hand-crafted byte buffers.** Mitigation: we synthesize `Uint8Array`s inline in the test (no binary fixture files checked into the repo).

## Migration Plan

No migration needed. The change is purely additive at runtime:
- Existing downloads with readable `Content-Type` or URL extensions: identical behavior.
- Downloads that would previously produce `.bin`: now produce the correct extension when the blob has a recognizable signature.

No data format, protocol, or database schema change. Rolling back is a straight revert of the three touched files.
